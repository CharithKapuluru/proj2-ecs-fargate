3.1 VERIFY AWS IDENTITY
------------------------

Command:
--------
aws sts get-caller-identity

What This Command Does:
------------------------
Asks AWS: "Who am I?"

Output:
-------
{
    "UserId": "AIDAXJWZ62WC3IC6Z27KW",
    "Account": "501894534533",
    "Arn": "arn:aws:iam::501894534533:user/test_user"
}

Breaking Down the Output:
--------------------------

Field 1: UserId
---------------
"UserId": "AIDAXJWZ62WC3IC6Z27KW"

What it is: A unique identifier for your IAM user.

Format breakdown:
AIDAXJWZ62WC3IC6Z27KW
│││
│││└─ Random unique string
││└── IAM type identifier
│└─── Always "A" for IAM identities
└──── Type: "AIDA" = IAM user

Other prefixes:
- AIDA: IAM user
- AROA: IAM role
- ASIA: Temporary security credentials (STS)
- AKIA: Access key

Real-world analogy: Like your Social Security Number - permanent and unique.

Why it matters:
- AWS uses this internally to track who does what
- Appears in CloudTrail logs
- Tied to all your permissions

Field 2: Account
----------------
"Account": "501894534533"

What it is: Your AWS account number.

Format:
- Always 12 digits
- Unique across all AWS accounts globally
- Cannot be changed

Real-world analogy: Like your bank account number.

Why it matters:
- All resources belong to this account
- Billing goes to this account
- Used in ARNs (Amazon Resource Names)
- Needed for cross-account access

Security note:
Account numbers are NOT secret. They're safe to share (unlike passwords).

Field 3: Arn
------------
"Arn": "arn:aws:iam::501894534533:user/test_user"

What it is: Amazon Resource Name - a full "address" for your IAM user.

ARN Structure:
--------------
arn:aws:iam::501894534533:user/test_user
│   │   │   │ │           │    │
│   │   │   │ │           │    └─── Resource name (test_user)
│   │   │   │ │           └────────── Resource type (user)
│   │   │   │ └────────────────────── Account number
│   │   │   └──────────────────────── (empty for global services)
│   │   └──────────────────────────── Service (iam)
│   └──────────────────────────────── Partition (aws = public cloud)
└──────────────────────────────────── Always starts with "arn"

Other ARN examples:
-------------------
S3 bucket:
arn:aws:s3:::my-bucket

EC2 instance:
arn:aws:ec2:us-east-1:501894534533:instance/i-1234567890abcdef0

Lambda function:
arn:aws:lambda:us-east-1:501894534533:function:my-function

RDS database:
arn:aws:rds:us-east-1:501894534533:db:my-database

Why ARNs matter:
- Uniquely identify every resource in AWS
- Used in IAM policies to grant permissions
- Required for cross-account access
- Appear in logs and audit trails

Real-world analogy:
ARN is like a full mailing address:
- Street number: test_user
- Street: user (resource type)
- City: (none - global service)
- State: 501894534533 (account)
- Country: iam (service)
- Planet: aws (partition)

How AWS CLI Gets This Information:
-----------------------------------

Step-by-step process:

```
┌────────────────────────────────────────────────────────────┐
│ Step 1: You type the command                               │
│   aws sts get-caller-identity                              │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 2: AWS CLI reads credentials                          │
│   Location: ~/.aws/credentials                             │
│                                                            │
│   [default]                                                │
│   aws_access_key_id = AKIAXJWZ62WCSNDTHYVE                │
│   aws_secret_access_key = <your-secret-key>               │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 3: AWS CLI creates signed request                    │
│                                                            │
│   Signature = HMAC-SHA256(                                │
│     secret_key +                                           │
│     request_details +                                      │
│     timestamp                                              │
│   )                                                        │
│                                                            │
│   This proves: "I own the secret key for this access key" │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 4: Sends HTTPS request to AWS                        │
│   URL: https://sts.us-east-1.amazonaws.com/                │
│   Headers:                                                 │
│     - Authorization: AWS4-HMAC-SHA256 Credential=...       │
│     - X-Amz-Date: 20260116T223000Z                        │
│     - Content-Type: application/x-www-form-urlencoded      │
│   Body:                                                    │
│     Action=GetCallerIdentity                               │
│     Version=2011-06-15                                     │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 5: AWS verifies signature                            │
│                                                            │
│   - Looks up access key: AKIAXJWZ62WCSNDTHYVE             │
│   - Finds it belongs to: test_user                         │
│   - Retrieves secret key from database                     │
│   - Recreates signature using same algorithm               │
│   - Compares signatures                                    │
│                                                            │
│   Match? ✓ Request is authentic                           │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 6: AWS checks permissions                            │
│                                                            │
│   Question: "Does test_user have permission for            │
│              sts:GetCallerIdentity?"                       │
│                                                            │
│   Checks IAM policies attached to test_user:               │
│   - AdministratorAccess policy                             │
│   - Allows: *:* (everything)                               │
│                                                            │
│   Answer: ✓ Yes, permission granted                       │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 7: AWS executes the action                           │
│                                                            │
│   Queries IAM database for identity information            │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 8: AWS returns response                              │
│   {                                                        │
│     "UserId": "AIDAXJWZ62WC3IC6Z27KW",                   │
│     "Account": "501894534533",                            │
│     "Arn": "arn:aws:iam::501894534533:user/test_user"   │
│   }                                                        │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ Step 9: AWS CLI displays result                           │
│   Formatted as JSON and printed to terminal                │
└────────────────────────────────────────────────────────────┘
```

Security: Your Secret Key Never Leaves Your Mac
------------------------------------------------

Important: The secret access key is NEVER sent over the internet!

What's transmitted:
✓ Access Key ID (public identifier)
✓ Signature (cryptographic proof)
✓ Timestamp
✓ Request details

What's NOT transmitted:
✗ Secret Access Key

Analogy:
--------
Traditional password login:
  Browser → "password123" → Server
  (Password sent in plain text - bad!)

AWS signing:
  AWS CLI → Creates signature with secret key → AWS
  (Only signature sent - good!)

Even if someone intercepts the signature, they:
- Cannot reverse it to get your secret key
- Cannot reuse it (includes timestamp, expires)
- Cannot forge new signatures without the secret key

This is like signing a check:
- Your signature proves you own the account
- But someone can't forge your signature from seeing it
- Each check is unique (different amount, date)

3.2 VERIFY AWS REGION
----------------------

Command:
--------
aws configure get region

What This Command Does:
------------------------
Reads your AWS CLI configuration file and returns the default region.

Output:
-------
us-east-1

What is an AWS Region?
----------------------

AWS Region = Physical location where AWS has data centers.

Each region:
- Has multiple data centers (Availability Zones)
- Is completely independent
- Has its own resources (isolated)
- Has different pricing
- Has different service availability

World Map of Major AWS Regions:
--------------------------------

North America:
├─ us-east-1 (N. Virginia) ← We're using this!
│  └─ Availability Zones: us-east-1a, us-east-1b, us-east-1c, us-east-1d, us-east-1e, us-east-1f
├─ us-east-2 (Ohio)
├─ us-west-1 (N. California)
├─ us-west-2 (Oregon)
└─ ca-central-1 (Canada)

South America:
└─ sa-east-1 (São Paulo)

Europe:
├─ eu-west-1 (Ireland)
├─ eu-west-2 (London)
├─ eu-west-3 (Paris)
├─ eu-central-1 (Frankfurt)
├─ eu-north-1 (Stockholm)
└─ eu-south-1 (Milan)

Asia Pacific:
├─ ap-south-1 (Mumbai)
├─ ap-northeast-1 (Tokyo)
├─ ap-northeast-2 (Seoul)
├─ ap-northeast-3 (Osaka)
├─ ap-southeast-1 (Singapore)
├─ ap-southeast-2 (Sydney)
└─ ap-east-1 (Hong Kong)

Middle East & Africa:
├─ me-south-1 (Bahrain)
└─ af-south-1 (Cape Town)

(+ many more GovCloud and China regions)

Why Regions Matter:
-------------------

Factor 1: Latency
-----------------
Distance = Speed

Your location: Texas
- us-east-1 (Virginia): ~40ms latency
- us-west-2 (Oregon): ~70ms latency
- eu-west-1 (Ireland): ~120ms latency
- ap-southeast-1 (Singapore): ~250ms latency

Users notice latency:
- < 50ms: Feels instant
- 50-100ms: Acceptable
- 100-200ms: Noticeable lag
- > 200ms: Frustrating

Rule: Choose region closest to your users.

Factor 2: Cost
--------------
Same service, different price!

Example: EC2 t3.medium instance (monthly):

| Region | Price/month |
|--------|-------------|
| us-east-1 (Virginia) | $30.37 |
| us-west-1 (California) | $33.41 |
| eu-west-1 (Ireland) | $32.85 |
| ap-southeast-1 (Singapore) | $35.04 |

us-east-1 is usually cheapest!

Factor 3: Service Availability
-------------------------------
New services launch in us-east-1 first.

Example timeline (typical):
- Day 0: Service launches in us-east-1
- Month 3: Expands to us-west-2, eu-west-1
- Month 6: Available in most regions
- Year 1+: Available globally

Some niche services: Only in us-east-1 forever

Factor 4: Data Residency
-------------------------
Some industries must keep data in specific countries.

Examples:
- GDPR (Europe): Data must stay in EU
- HIPAA (Healthcare): Data sovereignty requirements
- Government: Must use specific regions

Factor 5: Disaster Recovery
----------------------------
Multi-region for redundancy:
- Primary: us-east-1
- Backup: us-west-2

If us-east-1 has an outage:
- Failover to us-west-2
- Service continues

us-east-1 Details:
------------------

Official name: US East (N. Virginia)
Region code: us-east-1
Launch date: 2006 (first AWS region!)

Location:
Physical data centers in Northern Virginia, USA.

Availability Zones:
- us-east-1a
- us-east-1b
- us-east-1c
- us-east-1d
- us-east-1e
- us-east-1f

Fun facts:
- Oldest and largest AWS region
- Most services available here
- Cheapest pricing
- Most mature and stable
- Default for many AWS services

Downsides:
- More customers = higher chance you're affected by outages
- When us-east-1 goes down, half the internet breaks

Famous us-east-1 outages:
- December 2021: CloudWatch, EC2 issues
- November 2020: Kinesis failure
- February 2017: S3 outage (took down many websites)

Where Configuration is Stored:
-------------------------------

File: ~/.aws/config
```
[default]
region = us-east-1
output = json
```

File: ~/.aws/credentials
```
[default]
aws_access_key_id = AKIAXJWZ62WCSNDTHYVE
aws_secret_access_key = <secret>
```

Why separate files?
- config: Non-sensitive settings (region, output format)
- credentials: Sensitive data (access keys)

How AWS CLI Uses Region:
-------------------------

When you run: aws ecr create-repository --repository-name proj2-app

AWS CLI:
1. Reads region from ~/.aws/config: us-east-1
2. Constructs endpoint: https://ecr.us-east-1.amazonaws.com/
3. Sends request to that endpoint
4. Resource created in us-east-1

If you want a different region:
aws ecr create-repository --repository-name proj2-app --region us-west-2

This creates the repository in us-west-2, not us-east-1.

Important: Resources are region-specific!
------------------------------------------

If you create:
- VPC in us-east-1
- ECS cluster in us-west-2

They CANNOT talk to each other easily!

Rule: Keep all resources for one project in the same region.

What This Verification Tells Us:
---------------------------------

✅ Default region is us-east-1
✅ All resources will be created in us-east-1
✅ We won't accidentally create resources in expensive regions
✅ Configuration file is readable and correct

This is a complex command. Let's break it down completely.

What is AWS Budgets?
--------------------

AWS Budgets = Cost tracking and alerting service.

Features:
- Set spending limits
- Get email alerts when thresholds reached
- Track usage (GB, hours, etc.)
- Free for first 2 budgets per account

Real-world analogy:
Like a banking app that texts you when your balance is low.

Why we need it:
AWS bills can grow unexpectedly:
- Forgot to stop an EC2 instance: $100/month
- Load balancer running 24/7: $16/month
- Many small charges add up

Budget alert = Safety net

Parameter 1: Account ID
-----------------------
--account-id 501894534533

Why needed?
Budgets are account-wide. AWS needs to know which account.

Your account: 501894534533

Security note:
Only the account owner can create budgets for that account.

Parameter 2: Budget Definition
-------------------------------
--budget '{...}'

This is a JSON object defining the budget.

Field: BudgetName
-----------------
"BudgetName": "proj2-cost-guardrail"

What it is: Human-readable name for the budget.

Naming convention:
- proj2: Project identifier
- cost-guardrail: Purpose (prevent overspending)

Why it matters:
You might have multiple budgets:
- proj1-cost-guardrail
- proj2-cost-guardrail
- monthly-aws-spend
- ec2-instances-only

Names help you find the right budget.

Field: BudgetLimit
------------------
"BudgetLimit": {
  "Amount": "10",
  "Unit": "USD"
}

Amount: $10 per month
Unit: US Dollars

Why $10?
- Safe for learning project
- Covers basic testing
- Small enough that exceeding won't hurt

Expected costs for this project:
- ALB: ~$16-18/month if running 24/7
- Fargate (1 task): ~$7-8/month
- ECR: ~$0.10/month
- Logs: ~$0.50/month

Total if running 24/7: ~$24-28/month (over budget!)

Cost saving strategy:
- Only run when demoing (8 hours/day)
- Cost: ~$8/month (under budget!)
- Teardown when done

Field: TimeUnit
---------------
"TimeUnit": "MONTHLY"

Options:
- MONTHLY: Resets every month
- QUARTERLY: Resets every 3 months
- ANNUALLY: Resets once a year

How it works:
- January: Budget is $10
- You spend $8
- February 1st: Budget resets to $10 (spending starts at $0)
- March 1st: Budget resets again

We chose MONTHLY because:
- Most common billing cycle
- Easy to track
- Quick feedback if overspending

Field: BudgetType
-----------------
"BudgetType": "COST"

Options:
1. COST: Track spending in dollars (we chose this)
2. USAGE: Track resource usage (hours, GB, requests)
3. SAVINGS_PLANS_UTILIZATION: Advanced billing feature
4. RESERVATION_UTILIZATION: For reserved instances

We chose COST because:
- Simplest to understand
- Tracks what we care about (dollars spent)
- Matches how AWS bills you

Field: CostTypes
----------------
"CostTypes": {
  "IncludeTax": true,
  "IncludeSubscription": true,
  "UseBlended": false
}

Fine-tuning what costs to include.

IncludeTax: true
- Count taxes in the budget
- Some states charge sales tax on AWS
- Better to include (no surprises)

IncludeSubscription: true
- Count subscriptions (e.g., AWS Support Plans)
- We don't have any, but good to include

UseBlended: false
- Blended = Averaged pricing across multiple accounts
- We only have one account
- false = Use actual pricing

Most people use these defaults.

Parameter 3: Notifications and Subscribers
-------------------------------------------
--notifications-with-subscribers '[{...}]'

This is a JSON array of notification rules.

Structure:
```
[
  {
    "Notification": { ... },     ← When to alert
    "Subscribers": [ ... ]       ← Who to alert
  }
]
```

You can have multiple notifications:
- Alert at 50% to email
- Alert at 80% to email + SMS
- Alert at 100% to email + SNS topic

We have one: Alert at 80% to email.

Notification Object:
--------------------
"Notification": {
  "NotificationType": "ACTUAL",
  "ComparisonOperator": "GREATER_THAN",
  "Threshold": 80,
  "ThresholdType": "PERCENTAGE",
  "NotificationState": "ALARM"
}

Field: NotificationType
-----------------------
"NotificationType": "ACTUAL"

Options:
1. ACTUAL: Alert when you've actually spent the money (we chose this)
2. FORECASTED: Alert when AWS predicts you'll exceed the budget

ACTUAL example:
- Budget: $10
- Threshold: 80%
- Alert when: You've spent $8.01

FORECASTED example:
- Budget: $10
- Day 10 of month
- You've spent $5
- AWS predicts: You'll spend $15 by month end
- Alert triggered even though you've only spent $5

We chose ACTUAL because:
- More concrete (actual spending, not prediction)
- Simpler to understand
- Good enough for learning project

Field: ComparisonOperator
--------------------------
"ComparisonOperator": "GREATER_THAN"

Options:
- GREATER_THAN: Alert when above threshold (we chose this)
- LESS_THAN: Alert when below threshold
- EQUAL_TO: Alert when exactly at threshold

We use GREATER_THAN because:
We want to know when we exceed the limit.

Field: Threshold
----------------
"Threshold": 80

The number that triggers the alert.

Combined with ThresholdType (PERCENTAGE):
80% of $10 = $8

Alert triggers when spending > $8.

Why 80% instead of 100%?
- Early warning!
- Time to react before hitting limit
- Can stop resources before overspending

Common thresholds:
- 50%: First warning
- 75%: Second warning
- 90%: Final warning
- 100%: Limit exceeded

We use 80% for balance:
- Not too early (false alarms)
- Not too late (already over)

Field: ThresholdType
--------------------
"ThresholdType": "PERCENTAGE"

Options:
- PERCENTAGE: 80% of budget (we chose this)
- ABSOLUTE_VALUE: $8 (fixed amount)

PERCENTAGE is better because:
- Scales with budget
- Change budget to $20 → Alert at $16 automatically
- More flexible

Field: NotificationState
------------------------
"NotificationState": "ALARM"

What state to show in AWS Console.

Options:
- ALARM: Red/urgent (we chose this)
- OK: Green/normal

This is cosmetic - doesn't affect when alert triggers.

We chose ALARM because:
- Visually indicates urgency
- Red color grabs attention

Subscribers Array:
------------------
"Subscribers": [
  {
    "SubscriptionType": "EMAIL",
    "Address": "charith.kapuluru@unt.edu"
  }
]

Who gets notified.

Field: SubscriptionType
-----------------------
"SubscriptionType": "EMAIL"

Options:
- EMAIL: Send email (we chose this)
- SNS: Use Amazon SNS topic (advanced)

EMAIL is simpler:
- Just enter email address
- AWS handles sending
- No SNS setup needed

SNS is for advanced use:
- Send to multiple emails
- Send SMS
- Trigger Lambda function
- Integrate with Slack/PagerDuty

Field: Address
--------------
"Address": "charith.kapuluru@unt.edu"

Your email address for alerts.

Important: Must confirm subscription!
AWS sends confirmation email with link.
Must click link, or alerts won't work.

What Happens When Budget is Created:
-------------------------------------

Timeline:

4.1 HOW AWS CLI AUTHENTICATION WORKS
-------------------------------------

The Full Authentication Flow:
------------------------------

When you created your IAM user (test_user), you:
1. Logged into AWS Console as root user
2. Went to IAM → Users → Create User
3. Created user: test_user
4. Clicked "Create access key"
5. Downloaded the keys

AWS generated TWO keys:

Key 1: Access Key ID (Public)
------------------------------
AKIAXJWZ62WCSNDTHYVE

Properties:
- 20 characters
- Always starts with AKIA
- Safe to share (like a username)
- Identifies which IAM user

How it's used:
- Included in every AWS API request
- AWS looks it up to find the user
- Determines what permissions to check

Format breakdown:
AKIA XJWZ62WC SNDTHYVE
│    │         │
│    │         └─ Random identifier
│    └─────────── Access key identifier
└──────────────── Type prefix (always AKIA for IAM user keys)

Key 2: Secret Access Key (Private)
-----------------------------------
<40 random characters - never shown again after creation>

Properties:
- 40 characters
- Mix of letters, numbers, symbols
- SECRET! Never share
- Cannot be retrieved later

How it's used:
- Stays on your Mac only
- Used to sign requests
- Proves you own the access key
- Never transmitted over internet

Analogy:
- Access Key ID = Your username
- Secret Key = Your password

Configuration Files:
--------------------

File 1: ~/.aws/credentials
```
[default]
aws_access_key_id = AKIAXJWZ62WCSNDTHYVE
aws_secret_access_key = <your-secret-key>
```

Permissions: 600 (only you can read)

Created by: aws configure command

File 2: ~/.aws/config
```
[default]
region = us-east-1
output = json
```

Contains: Non-sensitive settings

Request Signing Process:
------------------------

Every AWS API call goes through this process:

Step 1: AWS CLI reads credentials
----------------------------------
Reads ~/.aws/credentials to get:
- Access Key ID
- Secret Access Key

Step 2: Create canonical request
---------------------------------
Formats the HTTP request in a standard way:

```
POST / HTTP/1.1
Host: sts.us-east-1.amazonaws.com
Content-Type: application/x-www-form-urlencoded
X-Amz-Date: 20260116T223000Z

Action=GetCallerIdentity&Version=2011-06-15
```

Step 3: Create string to sign
------------------------------
```
AWS4-HMAC-SHA256
20260116T223000Z
20260116/us-east-1/sts/aws4_request
<hash of canonical request>
```

Step 4: Calculate signature
----------------------------
```
signing_key = HMAC-SHA256(HMAC-SHA256(HMAC-SHA256(HMAC-SHA256(
  "AWS4" + secret_key,
  "20260116"),
  "us-east-1"),
  "sts"),
  "aws4_request")

signature = HMAC-SHA256(signing_key, string_to_sign)
```

This produces a hex string like:
1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcd

Step 5: Add authorization header
---------------------------------
```
Authorization: AWS4-HMAC-SHA256
Credential=AKIAXJWZ62WCSNDTHYVE/20260116/us-east-1/sts/aws4_request,
SignedHeaders=content-type;host;x-amz-date,
Signature=1234567890abcdef...
```

Step 6: Send HTTPS request
---------------------------
```
POST / HTTP/1.1
Host: sts.us-east-1.amazonaws.com
Authorization: AWS4-HMAC-SHA256 Credential=...
X-Amz-Date: 20260116T223000Z
Content-Type: application/x-www-form-urlencoded

Action=GetCallerIdentity&Version=2011-06-15
```

Step 7: AWS verifies signature
-------------------------------

AWS:
1. Receives request
2. Extracts Access Key ID from Authorization header
3. Looks up the Access Key in IAM database
4. Finds it belongs to: test_user
5. Retrieves the Secret Access Key for test_user
6. Performs the SAME signature calculation
7. Compares signatures

If they match:
✓ Request is authentic (sender owns the secret key)
✓ Request hasn't been tampered with
✓ Timestamp is recent (prevents replay attacks)

If they don't match:
✗ Request is rejected
✗ Returns 403 Forbidden

Step 8: Check permissions
--------------------------

AWS queries IAM:
"Does test_user have permission for sts:GetCallerIdentity?"

Checks policies attached to test_user:
- AdministratorAccess (allows everything)

Result: ✓ Permission granted

Step 9: Execute and return
---------------------------

AWS:
1. Executes GetCallerIdentity
2. Queries IAM database
3. Returns user information
4. Sends HTTP response

Security Features:
------------------

1. Signature includes timestamp
   - Prevents replay attacks
   - Old signatures rejected (> 15 minutes)

2. Signature includes request details
   - Changing URL invalidates signature
   - Changing body invalidates signature
   - Prevents request tampering

3. Secret key never transmitted
   - Only signature sent
   - Can't be intercepted
   - Can't be reversed

4. HTTPS encryption
   - All communication encrypted
   - Prevents eavesdropping

Comparison: Traditional Password Auth
--------------------------------------

Old way (bad):
```
Client → "password123" → Server
         (password in plain text!)
```

AWS way (good):
```
Client → Creates signature with secret key → AWS
         (only signature transmitted)
```

Benefits:
- Secret key never leaves your computer
- Signature can't be reused
- Signature can't be reversed to get key
- Each request has unique signature


4.2 HOW AWS REGIONS WORK
-------------------------

Physical Infrastructure:
------------------------

Each region consists of:

1. Multiple data centers (Availability Zones)
   - us-east-1a, us-east-1b, us-east-1c, etc.
   - Physically separate buildings
   - Miles apart
   - Independent power, cooling, networking

2. High-speed private network
   - Connects AZs within region
   - Low latency (< 2ms between AZs)
   - High bandwidth
   - Redundant connections

3. Complete isolation
   - Regions don't share infrastructure
   - Independent failure domains
   - Separate billing
   - Separate quotas

Region Architecture:
--------------------

```
Region: us-east-1
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  ┌──────────────────┐  ┌──────────────────┐              │
│  │ AZ: us-east-1a   │  │ AZ: us-east-1b   │              │
│  │                  │  │                  │              │
│  │ ┌──────────────┐ │  │ ┌──────────────┐ │              │
│  │ │ Data Center  │ │  │ │ Data Center  │ │              │
│  │ │ - Servers    │ │  │ │ - Servers    │ │              │
│  │ │ - Storage    │ │  │ │ - Storage    │ │              │
│  │ │ - Networking │ │  │ │ - Networking │ │              │
│  │ └──────────────┘ │  │ └──────────────┘ │              │
│  │                  │  │                  │              │
│  │ Your ECS Task →  │  │ Your ECS Task →  │              │
│  └────────┬─────────┘  └────────┬─────────┘              │
│           │                     │                         │
│           └──────────┬──────────┘                         │
│                      │                                    │
│                      ▼                                    │
│              ┌────────────────┐                           │
│              │ Load Balancer  │                           │
│              └────────┬───────┘                           │
│                       │                                   │
└───────────────────────┼───────────────────────────────────┘
                        │
                        ▼
                    Internet
```

Availability Zones (AZs):
--------------------------

What is an AZ?
- One or more data centers
- Within a region
- Independent infrastructure
- Isolated from failures in other AZs

Example: us-east-1
- us-east-1a: Data center cluster A
- us-east-1b: Data center cluster B
- us-east-1c: Data center cluster C
- us-east-1d: Data center cluster D
- us-east-1e: Data center cluster E
- us-east-1f: Data center cluster F

Distance between AZs:
- Far enough: Independent power grids, flood zones
- Close enough: Low latency networking (< 2ms)

Why multiple AZs matter:
- Redundancy: If one AZ fails, others continue
- High availability: Deploy across 2+ AZs
- Fault tolerance: AZ failures don't affect other AZs

Example:
Deploy ALB across us-east-1a and us-east-1b:
- Power outage in us-east-1a
- ALB in us-east-1b continues serving traffic
- No downtime

Resource Scope:
---------------

Global services (no region):
- IAM
- Route 53 (DNS)
- CloudFront (CDN)

Regional services:
- EC2 instances
- RDS databases
- S3 buckets (confusing: bucket name is global, data is regional)
- VPCs
- Load Balancers
- ECS clusters

AZ-specific resources:
- Subnets
- EC2 instances (in specific subnet)
- EBS volumes

Region Selection Factors:
--------------------------

Factor 1: Latency
-----------------

Speed of light limit:
- Signal travels ~200,000 km/second in fiber
- US East Coast to West Coast: ~4,500 km
- Minimum latency: ~45ms (round trip)

Practical latencies:
- Same region: 1-5ms
- Nearby regions: 20-80ms
- Across continents: 100-300ms

User experience:
- < 50ms: Feels instant
- 50-100ms: Acceptable
- 100-200ms: Noticeable delay
- > 200ms: Frustrating

Factor 2: Cost
--------------

Regional pricing differences (example: ALB):

| Region | $/hour | $/month (24/7) |
|--------|--------|----------------|
| us-east-1 | $0.0225 | $16.20 |
| us-west-2 | $0.0225 | $16.20 |
| us-west-1 | $0.025 | $18.00 |
| eu-central-1 | $0.025 | $18.00 |
| ap-southeast-1 | $0.028 | $20.16 |

us-east-1 is usually cheapest!

Factor 3: Compliance
--------------------

Data residency requirements:
- GDPR (EU): Data must stay in EU regions
- HIPAA (Healthcare): Must use certain regions
- Government: May require GovCloud regions

Factor 4: Service Availability
-------------------------------

Service launch timeline (typical):
- Month 0: Launches in us-east-1
- Month 3: us-west-2, eu-west-1
- Month 6: Major regions
- Year 1+: All regions

Some services: Only in us-east-1 for years

Cross-Region Communication:
---------------------------

Resources in different regions are isolated.

Example problem:
- VPC in us-east-1
- RDS in us-west-2
- Can't connect directly!

Solutions:
1. VPC Peering across regions
2. Transit Gateway
3. VPN connection
4. Public internet (not recommended)

Best practice: Keep everything in one region!

Budget Types Deep Dive:
------------------------

Type 1: COST Budget (we use this)
----------------------------------
Tracks: Dollar amount spent

Example:
- Budget: $10/month
- Current: $5.53
- Threshold: 80% = $8.00
- Alert when: Spent > $8.00

Use case: Most common - tracks your bill

Type 2: USAGE Budget
--------------------
Tracks: Amount of resource used (not dollars)

Example:
- Budget: 1000 EC2 instance-hours/month
- Current: 450 instance-hours
- Threshold: 80% = 800 instance-hours
- Alert when: Used > 800 hours

Use case: Control resource consumption independently of price changes

Type 3: SAVINGS PLANS UTILIZATION
----------------------------------
Tracks: How much of your Savings Plan you're using

Savings Plans = Discounted pricing for committed usage

Example:
- Committed: $100/month of compute
- Using: $70/month
- Utilization: 70%
- Alert when: Utilization < 90% (underutilizing)

Use case: Advanced cost optimization

Type 4: RESERVATION UTILIZATION
--------------------------------
Tracks: How much of your Reserved Instances you're using

Reserved Instances = Pre-purchased capacity at discount

Example:
- Reserved: 10 m5.large instances
- Running: 7 instances
- Utilization: 70%
- Alert when: Utilization < 80%

Use case: Ensure you're using what you paid for

Notification Types:
-------------------

Type 1: ACTUAL (we use this)
-----------------------------
Trigger: When you've actually spent the money

Example:
- Budget: $10
- Alert at: 80%
- Triggers when: You've spent $8.01

Delay: None (as soon as threshold crossed)

Type 2: FORECASTED
------------------
Trigger: When AWS predicts you'll exceed the budget

Example:
- Budget: $10
- Alert at: 80% forecasted
- Day 10 of month
- Spent so far: $4
- AWS forecast: You'll spend $13 by month end
- Alert triggers NOW (even though you've only spent $4)

How AWS forecasts:
- Analyzes spending trends
- Looks at same time last month
- Factors in day-of-week patterns
- Machine learning models

Use case: Early warning system

Threshold Types:
----------------

Type 1: PERCENTAGE (we use this)
---------------------------------
Threshold: 80% of budget

Benefit: Scales with budget changes

Example:
- Budget $10, threshold 80% = alert at $8
- Change budget to $20, threshold still 80% = alert at $16
- Don't need to update threshold

Type 2: ABSOLUTE_VALUE
-----------------------
Threshold: Fixed dollar amount

Example:
- Budget: $10
- Threshold: $8 (absolute)
- Alert when: Spent > $8

Downside:
- Change budget to $20
- Threshold still $8 (too early!)
- Need to manually update

Budget Aggregation:
-------------------

You can filter budgets by:
- Service (e.g., only EC2 costs)
- Linked account (for organizations)
- Tag (e.g., Project=proj2)
- Cost category
- Usage type

```json

  "BudgetName": "ec2-only",

```

Budget History:
---------------

AWS tracks:

- When alerts were triggered
- Historical spending vs budget
- Forecast accuracy

Useful for:

- Understanding seasonality
- Evaluating forecast accuracy

Budget Actions (Advanced):
---------------------------

Beyond email alerts, budgets can:
1. Apply IAM policy (block resource creation)
2. Apply SCP (for Organizations)
3. Stop EC2/RDS instances

Example: Auto-stop when budget exceeded
```json

    "ActionThresholdType": "PERCENTAGE",
```

→ Apply DenyAllPolicy to user

4.4 IAM PERMISSIONS AND POLICIES
---------------------------------

What is IAM?
------------

IAM = Identity and Access Management

IAM controls:
- Who can access AWS (authentication)
- What they can do (authorization)
- Which resources they can access

IAM Components:
---------------

1. IAM Users
   - Individual people
   - Has permanent credentials
   - Example: test_user

2. IAM Groups
   - Collections of users
   - Easier permission management
   - Example: developers, admins

3. IAM Roles
   - Temporary credentials
   - Can be assumed by users, services, applications
   - Example: EC2 instance role

4. IAM Policies
   - JSON documents defining permissions
   - Attached to users, groups, or roles
   - Example: AdministratorAccess

Your IAM Setup:
---------------

```
AWS Account: 501894534533 (root)
└─ IAM User: test_user
   ├─ Access Key: AKIAXJWZ62WCSNDTHYVE
   ├─ Secret Key: <your-secret>
   └─ Policy: AdministratorAccess
```

AdministratorAccess Policy:
----------------------------

This policy grants full access to everything.

Policy document:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
```

Translation:
- Effect: Allow (not Deny)
- Action: * (everything)
- Resource: * (all resources)

This is like: "Do anything to anything"

Why we use it:
- Learning project
- Need full access
- Don't want permission errors

Production best practice:
- Use least-privilege policies
- Only grant needed permissions
- Regularly audit permissions

IAM Policy Structure:
---------------------

Anatomy of a policy:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DescriptiveIdentifier",
      "Effect": "Allow" or "Deny",
      "Principal": {"AWS": "arn:..."} (for resource policies),
      "Action": ["service:Action", ...],
      "Resource": ["arn:...", ...],
      "Condition": {
        "ConditionOperator": {"key": "value"}
      }
    }
  ]
}
```

Example: S3 Read-Only Policy:
------------------------------
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ]
    }
  ]
}
```

Translation:
- Can: Get objects and list bucket
- From: my-bucket only
- Cannot: Delete, write, or access other buckets

Permission Evaluation:
----------------------

When test_user tries an action:

```
1. AWS collects all policies attached to test_user
   ├─ Directly attached policies
   ├─ Group policies
   └─ Inline policies

2. Default: Implicit DENY
   Everything is denied unless explicitly allowed

3. Check for explicit DENY
   If any policy denies → DENY (cannot override)

4. Check for explicit ALLOW
   If any policy allows → ALLOW

5. Result: ALLOW or DENY
```

Example:
```
test_user wants to: ecr:CreateRepository

Policies attached:
1. AdministratorAccess
   - Effect: Allow
   - Action: *
   - Resource: *

Evaluation:
1. Default: DENY
2. No explicit DENY found
3. AdministratorAccess explicitly allows * (everything)
4. Result: ALLOW ✓
```

Permission Boundaries (Advanced):
----------------------------------

Even with AdministratorAccess, some actions are restricted:

Root-only actions:
- Close AWS account
- Change account email
- Enable MFA on root
- Change AWS Support plan

Requires: Root user login (not IAM user)

test_user cannot do these, even with AdministratorAccess.

Service Control Policies (Organizations):
------------------------------------------

If your account is in an AWS Organization:
- SCP can override IAM policies
- Even AdministratorAccess can be restricted
- Example: SCP denies region us-west-1 → Can't use that region

Your account:
- Not in an Organization (standalone)
- No SCPs apply

5.1 WHAT IS ECR?
----------------

ECR = Elastic Container Registry

Purpose:
Store and manage Docker container images in AWS.

Real-world analogy:
Like GitHub, but for Docker images instead of source code.

Why we need it:
- ECS pulls images from ECR (not from your laptop)
- Private (only your AWS account can access)
- Fast (optimized for AWS services)
- Secure (encrypted, scanned for vulnerabilities)

ECR vs Docker Hub:
------------------

| Feature | Docker Hub | AWS ECR |
|---------|------------|---------|
| Accessibility | Public | Private (your account) |
| Cost | Free tier: 1 private repo | Pay per GB stored + data transfer |
| Speed to ECS | Slower (public internet) | Faster (AWS internal network) |
| Security | Basic | Image scanning, encryption |
| Integration | Any platform | Optimized for AWS |

ECR Structure:
--------------

```
AWS Account: 501894534533
└─ ECR Service (us-east-1)
   ├─ Repository: proj2-app
   │  ├─ Image: v1 (tag)
   │  ├─ Image: v2 (tag)
   │  └─ Image: latest (tag)
   ├─ Repository: another-app
   │  └─ Image: v1.0.0
   └─ Repository: third-app
      └─ Image: production
```

Repository = Folder for one app's images
Tag = Version label

ECR Registry URL:
-----------------
501894534533.dkr.ecr.us-east-1.amazonaws.com
│           │   │   │           │
│           │   │   │           └─ AWS domain
│           │   │   └────────────── Region
│           │   └────────────────── ECR service
│           └────────────────────── Docker registry marker
└────────────────────────────────── Account ID

This is like your personal Docker Hub domain.

ECR Features:
-------------

1. Image Scanning
   - Scans for security vulnerabilities
   - Checks OS packages, libraries
   - Generates vulnerability report
   - Free feature

2. Encryption at Rest
   - Images encrypted on disk
   - AES-256 encryption
   - Automatic (no setup needed)

3. Encryption in Transit
   - HTTPS for all transfers
   - Protects during push/pull

4. Lifecycle Policies
   - Auto-delete old images
   - Example: Keep only last 10 images
   - Saves storage costs

5. Image Replication
   - Copy images across regions
   - For disaster recovery
   - For lower latency in other regions

ECR Costs:
----------

Storage: $0.10 per GB-month
- Our image: ~50 MB = 0.05 GB
- Cost: $0.005/month (half a cent!)

Data Transfer:
- Out to internet: $0.09/GB
- Out to ECS in same region: FREE!

We'll use: ~$0.01/month total


5.2 WHAT IS ECS?
----------------

ECS = Elastic Container Service

Purpose:
Run Docker containers on AWS without managing servers.

Real-world analogy:
Like Heroku or Railway, but with more control and AWS integration.

Why we need it:
- Run our Flask app in production
- Automatic scaling
- Health checks and auto-restart
- Load balancer integration

ECS Components:
---------------

1. Cluster
   - Logical grouping of resources
   - Example: proj2-cluster

2. Task Definition
   - Blueprint for containers
   - Specifies: image, CPU, memory, ports

3. Task
   - Running instance of task definition
   - Like: container instance

4. Service
   - Keeps tasks running
   - Maintains desired count
   - Integrates with load balancer

5. Container
   - Your actual application
   - Running inside a task

Hierarchy:
```
Cluster: proj2-cluster
└─ Service: proj2-service
   ├─ Task 1
   │  └─ Container: Flask app
   └─ Task 2
      └─ Container: Flask app
```

ECS Launch Types:
-----------------

Type 1: Fargate (we use this)
------------------------------
- Serverless
- No EC2 instances to manage
- Pay per vCPU-second and GB-second
- Simpler

How it works:
- You define task (image, CPU, memory)
- AWS runs it somewhere
- You don't see or manage the server

Type 2: EC2
-----------
- You manage EC2 instances
- ECS schedules containers on your instances
- More control
- More work

How it works:
- Launch EC2 instances
- Register them to ECS cluster
- ECS places containers on instances

We chose Fargate:
- Simpler (no instance management)
- Good for learning
- Good for low-scale apps

Task Definition:
----------------

Specifies:
- Docker image
- CPU allocation (256, 512, 1024, ...)
- Memory allocation (512 MB, 1 GB, ...)
- Port mappings
- Environment variables
- Logging configuration
- IAM role

Example:
```json
{
  "family": "proj2-task",
  "cpu": "256",
  "memory": "512",
  "containerDefinitions": [
    {
      "name": "proj2-app",
      "image": "501894534533.dkr.ecr.us-east-1.amazonaws.com/proj2-app:v1",
      "portMappings": [
        {
          "containerPort": 8080,
          "protocol": "tcp"
        }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/proj2-app",
          "awslogs-region": "us-east-1",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

ECS Service:
------------

Maintains desired task count.

Example:
- Desired count: 2
- Running: 2
- One crashes
- Service starts new task
- Running: 2 again (recovered!)

Service features:
- Load balancer integration
- Auto-scaling (optional)
- Rolling deployments
- Health checks

Service Scheduler:
------------------

How ECS decides where to run tasks:
1. Check available capacity
2. Check task requirements (CPU, memory)
3. Check constraints (AZ, instance type)
4. Find best placement
5. Launch task

Fargate is simpler:
AWS handles all this automatically.

Pricing:
- Per vCPU-hour: $0.04048
- Per GB-hour: $0.004445

Our task (256 CPU, 512 MB):
- CPU: 0.25 vCPU × $0.04048 = $0.01012/hour
- Memory: 0.5 GB × $0.004445 = $0.002222/hour

If running 24/7.

5.3 WHAT IS VPC?
----------------

VPC = Virtual Private Cloud

Purpose:
Your own private network in AWS.

Real-world analogy:
Like having your own building with:
- Private rooms (subnets)
- Security guards (security groups)
- Controlled entrances (internet gateway)

Why we need it:
- Network isolation
- Control traffic flow
- Security
- Multi-tier architecture

VPC Components:
---------------

1. VPC
   - Main network
   - CIDR block: 10.0.0.0/16

2. Subnets
   - Subdivisions of VPC
   - Public: Has internet access
   - Private: No direct internet access

3. Internet Gateway
   - Connects VPC to internet
   - Required for public subnets

4. Route Tables
   - Defines network routing
   - Directs traffic

5. Security Groups
   - Firewall rules
   - Controls inbound/outbound traffic

6. Network ACLs
   - Subnet-level firewall
   - Stateless (unlike security groups)

VPC CIDR Blocks:
----------------

CIDR = Classless Inter-Domain Routing

Example: 10.0.0.0/16
- Network: 10.0.0.0
- Mask: /16
- IP range: 10.0.0.0 to 10.0.255.255
- Total IPs: 65,536

Breaking down /16:
- 32 bits total (IPv4)
- 16 bits for network (fixed)
- 16 bits for hosts (variable)
- 2^16 = 65,536 addresses

Subnet example: 10.0.1.0/24
- Network: 10.0.1.0
- Mask: /24
- IP range: 10.0.1.0 to 10.0.1.255
- Total IPs: 256

Breaking down /24:
- 24 bits for network
- 8 bits for hosts
- 2^8 = 256 addresses

Private IP Ranges:
------------------

RFC 1918 reserves these for private networks:
- 10.0.0.0/8 (10.0.0.0 to 10.255.255.255)
- 172.16.0.0/12 (172.16.0.0 to 172.31.255.255)
- 192.168.0.0/16 (192.168.0.0 to 192.168.255.255)

These are NOT routable on public internet.

Our VPC: 10.0.0.0/16
Our subnets:
- 10.0.1.0/24 (public subnet 1)
- 10.0.2.0/24 (public subnet 2)

Public vs Private Subnets:
--------------------------

Public Subnet:
- Has route to Internet Gateway
- Resources can have public IPs
- Can access internet directly

Route table:
```
Destination      Target
10.0.0.0/16      local (within VPC)
0.0.0.0/0        igw-xxxxx (internet gateway)
```

Private Subnet:
- No route to Internet Gateway
- Resources have private IPs only
- Can't access internet directly

Route table:
```
Destination      Target
10.0.0.0/16      local (within VPC)
```

For internet access from private subnet:
- NAT Gateway (in public subnet)
- VPC Endpoints (for AWS services)

Security Groups:
----------------

Security Group = Firewall for resources

Rules:
- Inbound: Traffic coming IN to resource
- Outbound: Traffic going OUT from resource

Example: ALB Security Group
```
Inbound:
- Port 80, Source: 0.0.0.0/0 (internet)

Outbound:
- All traffic to ECS security group
```

Example: ECS Security Group
```
Inbound:
- Port 8080, Source: ALB security group only

Outbound:
- Port 443 to 0.0.0.0/0 (for pulling images, etc.)
```

Security Group features:
- Stateful (return traffic automatic)
- Instance-level (not subnet-level)
- Allow rules only (no deny rules)

Default VPC:
------------

AWS automatically creates a default VPC in each region.

Features:
- CIDR: 172.31.0.0/16
- Subnets: One per AZ (public)
- Internet Gateway: Attached
- Default security group

Why we don't use it:
- Learning opportunity
- Production best practice: Custom VPC
- More control over architecture

VPC Costs:
----------

VPC itself: FREE
Internet Gateway: FREE
Subnets: FREE
Route Tables: FREE
Security Groups: FREE

Paid components:
- NAT Gateway: ~$0.045/hour = $32.40/month
- VPN: ~$0.05/hour
- VPC Endpoints: ~$0.01/hour per endpoint

We won't use NAT Gateway (use public subnets for tasks).

6. TROUBLESHOOTING COMMON ISSUES
================================================================================

Issue 1: Access Denied Errors
------------------------------

Error:
```
An error occurred (AccessDeniedException) when calling the
DescribeRepositories operation: User: arn:aws:iam::501894534533:user/test_user
is not authorized to perform: ecr:DescribeRepositories
```

Cause:
IAM user lacks required permissions.

Solutions:

1. Check attached policies:
   aws iam list-attached-user-policies --user-name test_user

2. If no AdministratorAccess:
   - Log in as root user
   - Go to IAM → Users → test_user
   - Attach AdministratorAccess policy

3. If still failing:
   - Check for explicit DENY policies
   - Check Service Control Policies (if in Organization)


Issue 2: Wrong Region
----------------------

Error:
Resources created in wrong region (e.g., us-west-2 instead of us-east-1).

Cause:
Region not set correctly.

Solutions:

1. Check current region:
   aws configure get region

2. If wrong, set it:
   aws configure set region us-east-1

3. Always specify --region flag:
   aws ecr create-repository --repository-name proj2-app --region us-east-1


Issue 3: Budget Not Sending Emails
-----------------------------------

Symptom:
Budget exceeds threshold, but no email received.

Causes and solutions:

Cause A: Email not confirmed
Solution:
- Check email for "AWS Budget Notification Subscription Confirmation"
- Click confirmation link
- If email not received, check spam folder

Cause B: Wrong email address
Solution:
- Verify subscriber:
  aws budgets describe-subscribers-for-notification ...
- If wrong, delete and recreate budget with correct email

Cause C: Threshold not reached
Solution:
- Check current spending:
  aws budgets describe-budgets --account-id 501894534533
- Spending must exceed threshold to trigger


Issue 4: Invalid Credentials
-----------------------------

Error:
```
An error occurred (InvalidClientTokenId) when calling the GetCallerIdentity
operation: The security token included in the request is invalid.
```

Cause:
Access key invalid or deleted.

Solutions:

1. Check credentials file:
   cat ~/.aws/credentials

2. Verify access key exists:
   - Log into AWS Console as root
   - IAM → Users → test_user → Security credentials
   - Check if access key is listed and Active

3. If deleted, create new access key:
   - Create access key
   - Run: aws configure
   - Enter new access key ID and secret


Issue 5: Budget Command Fails
------------------------------

Error:
```
Parameter validation failed:
Unknown parameter in Budget: "..."
```

Cause:
JSON syntax error in budget definition.

Solutions:

1. Validate JSON:
   - Copy budget JSON to a file
   - Use online JSON validator
   - Check for:
     - Missing commas
     - Extra commas
     - Missing quotes
     - Missing brackets

2. Use JSON file instead of inline:
   aws budgets create-budget --cli-input-json file://budget.json


Issue 6: Account ID Confusion
------------------------------

Symptom:
Commands reference wrong account ID.

Cause:
Copied commands without replacing account ID.

Solution:
Always replace 501894534533 with YOUR actual account ID.

Get your account ID:
aws sts get-caller-identity --query Account --output text
