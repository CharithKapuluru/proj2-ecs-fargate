1. INTRODUCTION TO AWS MONITORING
================================================================================

Why Monitoring Matters
----------------------
In production systems, you need to know:
- Is my application healthy?
- How many requests am I handling?
- Are there errors occurring?
- Is the system under stress?
- When do problems happen?

Without monitoring:
- You discover issues when users complain
- No historical data to diagnose problems
- Can't predict capacity needs
- No evidence of system behavior

With monitoring:
- Proactive issue detection via alarms
- Historical data for debugging
- Capacity planning insights
- SLA compliance evidence

AWS Monitoring Components
-------------------------

1. **CloudWatch Metrics**: Time-series data points
   - CPU usage, memory, request counts, etc.
   - Collected automatically for AWS services
   - Custom metrics possible via SDK

2. **CloudWatch Alarms**: Automated threshold monitoring
   - Trigger when metric crosses threshold
   - Send notifications via SNS
   - Can trigger auto-scaling

3. **CloudWatch Logs**: Centralized logging
   - Application logs from containers
   - Searchable and filterable
   - Already set up in Phase E

4. **CloudWatch Dashboards**: Visual monitoring
   - Real-time metrics visualization
   - Customizable layouts
   - Shareable with team

5. **SNS (Simple Notification Service)**: Notification delivery
   - Email, SMS, HTTP endpoints
   - Pub/sub messaging
   - Integrates with alarms

Observability Pillars
---------------------
Professional monitoring follows three pillars:

1. **Metrics**: Numeric measurements over time
   - CPU utilization: 45%
   - Request count: 1000/minute
   - Error rate: 0.5%

2. **Logs**: Detailed event records
   - "2024-01-17 10:30:00 - GET /health - 200"
   - Stack traces, debug info
   - Set up in Phase E

3. **Traces**: Request flow through systems
   - Request → ALB → ECS → Response
   - Latency breakdown
   - Not covered (advanced topic)

Phase F focuses on Metrics and Alerts.

3. SNS (SIMPLE NOTIFICATION SERVICE) DEEP DIVE
================================================================================

What is SNS?
------------
SNS is AWS's fully managed pub/sub messaging service. It enables:
- Send messages to multiple subscribers
- Fan-out to different endpoints
- Decouple producers from consumers

Key Concepts:
- **Topic**: A communication channel
- **Publisher**: Sends messages to topics
- **Subscriber**: Receives messages from topics
- **Subscription**: Links subscriber to topic

SNS Topic Configuration
-----------------------
```hcl
resource "aws_sns_topic" "alerts" {
  name = "proj2-alerts"

  tags = {
    Name = "proj2-alerts"
  }
}
```

Simple topic creation. The topic acts as a message hub.

Topic Policy
------------
```hcl
resource "aws_sns_topic_policy" "alerts_policy" {
  arn = aws_sns_topic.alerts.arn

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "AllowCloudWatchAlarms"
        Effect    = "Allow"
        Principal = {
          Service = "cloudwatch.amazonaws.com"
        }
        Action   = "sns:Publish"
        Resource = aws_sns_topic.alerts.arn
      }
    ]
  })
}
```

This policy allows CloudWatch Alarms to send notifications to our topic.

Without this policy:
- CloudWatch couldn't publish alarm state changes
- You'd never receive notifications

Email Subscription
------------------
```hcl
resource "aws_sns_topic_subscription" "email" {
  topic_arn = aws_sns_topic.alerts.arn
  protocol  = "email"
  endpoint  = var.alert_email
}
```

Creates an email subscription.

**CRITICAL**: After terraform apply, you MUST:
1. Check your email inbox
2. Find email from "AWS Notifications"
3. Click "Confirm subscription" link
4. Subscription becomes active

Without confirmation:
- Subscription stays "pending"
- No emails are delivered
- Alarms trigger but you never know

Other Subscription Protocols
----------------------------
SNS supports multiple delivery methods:

| Protocol | Use Case |
|----------|----------|
| email | Human notifications |
| email-json | Machine-parseable email |
| sms | Text message alerts |
| http/https | Webhook to your app |
| lambda | Trigger AWS Lambda |
| sqs | Queue messages |
| application | Mobile push notifications |

You could add multiple subscriptions:
```hcl
# Example: Add SMS (not in our code)
resource "aws_sns_topic_subscription" "sms" {
  topic_arn = aws_sns_topic.alerts.arn
  protocol  = "sms"
  endpoint  = "+1234567890"
}
```

How SNS Message Flow Works
--------------------------
```
1. CloudWatch Alarm triggers (CPU > 80%)
              │
              ▼
2. Alarm publishes to SNS Topic (proj2-alerts)
              │
              ▼
3. SNS checks subscriptions
              │
              ▼
4. For each confirmed subscription:
   - Email: Send formatted email
   - SMS: Send text message
   - HTTP: POST to endpoint
              │
              ▼
5. You receive: "ALARM: proj2-ecs-cpu-high"
```

SNS Message Format (Email)
--------------------------
When an alarm triggers, you receive:

Subject: ALARM: "proj2-ecs-cpu-high" in US East (N. Virginia)

Body:
```

the ALARM state, because "Threshold Crossed: 1 datapoint [85.0] was

View this alarm in the AWS Management Console:
https://console.aws.amazon.com/cloudwatch/...

Alarm Details:
- Name:                       proj2-ecs-cpu-high

```

4. CLOUDWATCH ALARMS EXPLAINED
================================================================================

What is a CloudWatch Alarm?
---------------------------
An alarm watches a single metric and triggers when:
- Metric crosses a threshold
- For a specified number of evaluation periods
- Optionally, sends notifications

Alarm States:
- **OK**: Metric is within threshold
- **ALARM**: Metric has crossed threshold
- **INSUFFICIENT_DATA**: Not enough data to evaluate

Alarm Anatomy
-------------
```hcl
resource "aws_cloudwatch_metric_alarm" "example" {
  alarm_name          = "unique-alarm-name"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "CPUUtilization"
  namespace           = "AWS/ECS"
  period              = 60
  statistic           = "Average"
  threshold           = 80
  alarm_description   = "Human-readable description"
  treat_missing_data  = "notBreaching"

  dimensions = {
    ClusterName = "my-cluster"
    ServiceName = "my-service"
  }

  alarm_actions = [aws_sns_topic.alerts.arn]
  ok_actions    = [aws_sns_topic.alerts.arn]
}
```

Let's break down each parameter:

**comparison_operator**: How to compare metric to threshold
- GreaterThanThreshold
- GreaterThanOrEqualToThreshold
- LessThanThreshold
- LessThanOrEqualToThreshold

**evaluation_periods**: How many periods must breach
- 2 means "must breach in 2 consecutive periods"
- Prevents false alarms from spikes

**metric_name**: Which metric to watch
- AWS provides hundreds of metrics
- Custom metrics also possible

**namespace**: Metric grouping
- AWS/ECS for ECS metrics
- AWS/ApplicationELB for ALB metrics
- Custom for your own metrics

**period**: Evaluation interval (seconds)
- 60 = check every minute
- 300 = check every 5 minutes

**statistic**: How to aggregate data points
- Average, Sum, Minimum, Maximum
- SampleCount, pNN (percentile)

**threshold**: The comparison value

**treat_missing_data**: What if no data?
- notBreaching: Assume OK (our choice)
- breaching: Assume ALARM
- ignore: Maintain current state
- missing: Treat as missing

**dimensions**: Narrow the metric scope
- Which cluster? Which service?
- Without dimensions, alarm watches all

**alarm_actions**: What to do when ALARM
- SNS topic ARN for notifications
- Can also trigger Auto Scaling

**ok_actions**: What to do when returns to OK
- Also notifies, so you know issue resolved

Our Alarms Explained
--------------------

**1. ECS CPU High (proj2-ecs-cpu-high)**
```hcl
metric_name         = "CPUUtilization"
namespace           = "AWS/ECS"
threshold           = 80
comparison_operator = "GreaterThanThreshold"
evaluation_periods  = 2
period              = 60
```

Triggers when: ECS CPU > 80% for 2 consecutive minutes

Why this matters:
- High CPU indicates container is overloaded
- May need to scale up (more tasks)
- Application might become slow

**2. ECS Memory High (proj2-ecs-memory-high)**
```hcl
metric_name         = "MemoryUtilization"
namespace           = "AWS/ECS"
threshold           = 80
```

Triggers when: ECS Memory > 80% for 2 consecutive minutes

Why this matters:
- High memory could cause OOM kills
- Application might crash
- Need larger task or more tasks

**3. ALB 5XX Errors (proj2-alb-5xx-errors)**
```hcl
metric_name         = "HTTPCode_ELB_5XX_Count"
namespace           = "AWS/ApplicationELB"
threshold           = 10
statistic           = "Sum"
```

Triggers when: ALB returns > 10 5XX errors in a minute

What are 5XX errors?
- 500: Internal Server Error
- 502: Bad Gateway (backend not responding)
- 503: Service Unavailable (no healthy targets)
- 504: Gateway Timeout

Why this matters:
- Users are experiencing errors
- Something is broken

**4. Target 5XX Errors (proj2-target-5xx-errors)**
```hcl
metric_name         = "HTTPCode_Target_5XX_Count"
threshold           = 5
```

Triggers when: ECS containers return > 5 5XX errors

Difference from ALB 5XX:
- ALB 5XX: ALB itself failed (networking issues)
- Target 5XX: Your application failed (bugs, crashes)

**5. Unhealthy Hosts (proj2-unhealthy-hosts)**
```hcl
metric_name         = "UnHealthyHostCount"
threshold           = 0
comparison_operator = "GreaterThanThreshold"
```

Triggers when: Any target becomes unhealthy

Why this matters:
- Unhealthy = failed health checks
- Container might be crashed
- ECS should restart it automatically

**6. High Latency (proj2-high-latency)**
```hcl
metric_name         = "TargetResponseTime"
threshold           = 2
evaluation_periods  = 3
```

Triggers when: Average response time > 2 seconds for 3 minutes

Why this matters:
- Slow responses = poor user experience
- Might indicate overload or bug
- SLA violations

**7. No Healthy Hosts - CRITICAL (proj2-no-healthy-hosts-CRITICAL)**
```hcl
metric_name         = "HealthyHostCount"
threshold           = 1
comparison_operator = "LessThanThreshold"
treat_missing_data  = "breaching"
```

Triggers when: Healthy host count < 1 (zero healthy hosts)

This is CRITICAL because:
- No healthy hosts = service is DOWN
- All requests return 503
- Immediate action needed

Note: treat_missing_data = "breaching" here because:
- If we can't even get the metric, something is very wrong
- Better to alert than miss an outage

Alarm Evaluation Timeline
-------------------------
Example: CPU alarm with threshold=80, evaluation_periods=2, period=60

```
Time    | CPU  | Evaluation
--------|------|------------------
10:00   | 75%  | OK (below 80)
10:01   | 85%  | Breach 1 of 2
10:02   | 82%  | Breach 2 of 2 → ALARM!
10:03   | 70%  | OK 1 of 2
10:04   | 65%  | OK 2 of 2 → OK state
```

The 2-period requirement prevents:
- Single spike causing alarm
- Flapping between OK/ALARM
- Alert fatigue

What is a CloudWatch Dashboard?
-------------------------------
A dashboard is a customizable page displaying metrics visualizations.

Benefits:
- Single view of system health
- Real-time data
- Shareable with team
- No additional cost (up to 3 free dashboards)

Dashboard Configuration
-----------------------
```hcl
resource "aws_cloudwatch_dashboard" "proj2" {
  dashboard_name = "proj2-dashboard"
  dashboard_body = jsonencode({ widgets = [...] })
}
```

The dashboard body is JSON defining widgets.

Widget Types
------------
Our dashboard uses several widget types:

1. **Text Widget**: Markdown titles/notes
2. **Metric Widget**: Line graphs, bar charts
3. **Log Widget**: Recent log entries
4. **Single Value**: Big number display

Widget Positioning
------------------
Dashboards use a 24-column grid:
- x: Left position (0-23)
- y: Top position (0+)
- width: Columns to span (1-24)
- height: Rows to span

Example layout:
```
┌────────────────────────────────────────────────────────────────────┐
│ Row 0: Title (full width)                                    y=0  │
├────────────────┬────────────────┬────────────────┬────────────────┤
│ Requests       │ Response Time  │ Healthy Hosts  │                │
│ x=0, w=8       │ x=8, w=8       │ x=16, w=8      │           y=1  │
├────────────────┴────────────────┼────────────────┴────────────────┤
│ HTTP Status Codes               │ Error Rate                      │
│ x=0, w=12                       │ x=12, w=12                 y=7  │
├────────────────┬────────────────┴────────────────┬────────────────┤
│ CPU            │ Memory                          │           y=13 │
├────────────────┴─────────────────────────────────┴────────────────┤
│ Application Logs                                             y=25 │
└────────────────────────────────────────────────────────────────────┘
```

Our Dashboard Widgets
---------------------

**Row 1: Title**
```json
{
  "type": "text",
  "properties": {
    "markdown": "# Proj2 ECS Fargate Application Dashboard"
  }
}
```

**Row 2: Key Metrics**
- Request Count (total requests per minute)
- Response Time (average and p99 latency)
- Healthy vs Unhealthy Hosts

**Row 3: Error Tracking**
- HTTP Status Codes (2XX, 4XX, 5XX breakdown)
- Error Rate (percentage calculation)

**Row 4: Resource Utilization**
- ECS CPU Utilization (with 80% threshold line)
- ECS Memory Utilization (with 80% threshold line)

**Row 5: Connections**
- Running Task Count
- Active Connections
- New Connections per Second

**Row 6: Logs**
- Recent application logs from CloudWatch Logs

Metric Math Example
-------------------
The Error Rate widget uses metric math:

```json
{
  "expression": "(m2+m3)/(m1+m2+m3)*100",
  "label": "Error Rate %",
  "id": "e1"
}
```

This calculates:
- m1 = 2XX count (success)
- m2 = 4XX count (client errors)
- m3 = 5XX count (server errors)
- Error Rate = (4XX + 5XX) / (2XX + 4XX + 5XX) * 100

Annotations
-----------
We add threshold lines to CPU/Memory widgets:

```json
"annotations": {
  "horizontal": [
    { "value": 80, "label": "Alarm Threshold", "color": "#d62728" }
  ]
}
```

This draws a red line at 80% so you can see how close you are to triggering alarms.

7. HOW ALERTING WORKS END-TO-END
================================================================================

Complete Alert Flow Example
---------------------------
Scenario: CPU spikes due to traffic surge

```
Time: 10:00
─────────────────────────────────────────────────────────────────────────
Flask app receives burst of requests
ECS task CPU jumps to 85%
CloudWatch collects CPUUtilization metric from ECS
Alarm "proj2-ecs-cpu-high" evaluates: 85% > 80%? YES
Evaluation: Breach 1 of 2 (need consecutive breaches)
State: OK (not yet alarming)

Time: 10:01
─────────────────────────────────────────────────────────────────────────
CPU still at 83%
Alarm evaluates: 83% > 80%? YES
Evaluation: Breach 2 of 2
State: OK → ALARM

Alarm publishes to SNS topic "proj2-alerts":
{
  "AlarmName": "proj2-ecs-cpu-high",
  "NewStateValue": "ALARM",
  "NewStateReason": "Threshold Crossed: 2 datapoints..."
}

SNS checks subscriptions:
- Email (kapulurucharith@gmail.com): Confirmed ✓

SNS sends email:
Subject: ALARM: "proj2-ecs-cpu-high" in US East (N. Virginia)
Body: [Alarm details, link to console]

Time: 10:02
─────────────────────────────────────────────────────────────────────────
You receive email notification
Check CloudWatch dashboard
See CPU spike in graph
Investigate cause (traffic, bug, etc.)

Time: 10:05
─────────────────────────────────────────────────────────────────────────
Traffic normalizes
CPU drops to 45%
Alarm evaluates: 45% > 80%? NO
Evaluation: OK 1 of 2

Time: 10:06
─────────────────────────────────────────────────────────────────────────
CPU at 40%
Alarm evaluates: 40% > 80%? NO
Evaluation: OK 2 of 2
State: ALARM → OK

SNS sends "OK" notification:
Subject: OK: "proj2-ecs-cpu-high" in US East (N. Virginia)
Body: [Issue resolved details]

You know the incident is over
```

Multiple Alarm Correlation
--------------------------
Real incidents often trigger multiple alarms:

```
Incident: Container crash

10:00 - Container dies
10:01 - ALARM: proj2-unhealthy-hosts (unhealthy target detected)
10:01 - ALARM: proj2-target-5xx-errors (requests to dead container fail)
10:02 - ALARM: proj2-no-healthy-hosts-CRITICAL (if only 1 task)

10:03 - ECS restarts container
10:04 - Container passes health checks
10:05 - OK: proj2-no-healthy-hosts-CRITICAL
10:05 - OK: proj2-unhealthy-hosts
10:06 - OK: proj2-target-5xx-errors
```

The sequence of alarms helps diagnose the root cause.

Dashboard During Incident
-------------------------
When investigating, check the dashboard:

1. **Request Count**: Did traffic spike?
2. **Error Rate**: When did errors start?
3. **CPU/Memory**: Resource exhaustion?
4. **Healthy Hosts**: Did containers die?
5. **Response Time**: Gradual degradation?
6. **Logs**: Error messages?

9. KEY CONCEPTS SUMMARY
================================================================================

SNS Concepts
------------
- **Topic**: Message hub (proj2-alerts)
- **Subscription**: Endpoint receiving messages
- **Protocol**: Delivery method (email, sms, http)
- **Confirmation**: Email subscriptions need confirmation

CloudWatch Alarms
-----------------
- **Metric**: What to watch (CPUUtilization)
- **Namespace**: Metric category (AWS/ECS)
- **Threshold**: When to alarm (80%)
- **Evaluation Periods**: Consecutive breaches needed
- **Actions**: What to do (notify SNS)

CloudWatch Dashboard
--------------------
- **Widget**: Individual visualization
- **Metric Widget**: Line/bar charts
- **Text Widget**: Markdown text
- **Log Widget**: Recent log entries
- **Grid Layout**: 24-column positioning

Monitoring Best Practices
-------------------------
1. **Don't over-alert**: Too many alarms = ignored alarms
2. **Tune thresholds**: Adjust based on baseline
3. **Use evaluation periods**: Avoid false positives
4. **Alert on symptoms**: 5XX errors matter more than CPU
5. **Include OK notifications**: Know when issues resolve
6. **Document runbooks**: What to do when each alarm fires

10. COMMON ISSUES AND SOLUTIONS
================================================================================

Issue: Not receiving email alerts
---------------------------------
**Symptoms:**
- Alarm state changes but no email
- SNS shows "pending confirmation"

**Solutions:**
1. Check spam folder
2. Confirm subscription link in email
3. Verify email address is correct:
   ```bash
   terraform output -raw sns_topic_arn
   aws sns list-subscriptions-by-topic --topic-arn <arn>
   ```

Issue: All alarms show INSUFFICIENT_DATA
-----------------------------------------
**Symptoms:**
- Alarms never evaluate to OK or ALARM
- "Insufficient data" state

**Causes:**
- Metric doesn't exist yet
- Wrong dimensions
- ECS service not running

**Solutions:**
1. Verify ECS service is running and has tasks
2. Generate some traffic
3. Check metric exists:
   ```bash
   aws cloudwatch list-metrics --namespace AWS/ECS
   ```

Issue: Dashboard shows "No data available"
------------------------------------------
**Symptoms:**
- Widgets display "No data available"
- Graphs are empty

**Causes:**
- No traffic yet
- Wrong metric dimensions
- Time range issue

**Solutions:**
1. Generate traffic: `curl http://alb-url/`
2. Change dashboard time range to "1h" or "3h"
3. Verify metrics exist in CloudWatch console

Issue: Alarm flapping (OK → ALARM → OK rapidly)
-----------------------------------------------
**Symptoms:**
- Multiple notifications in short time
- Alarm keeps changing state

**Causes:**
- Threshold too close to normal
- evaluation_periods too low

**Solutions:**
1. Increase threshold (e.g., 80% → 85%)
2. Increase evaluation_periods (e.g., 2 → 3)
3. Increase period (e.g., 60s → 300s)

Issue: Missing permissions error
--------------------------------
**Symptoms:**
- Terraform apply fails
- "Access Denied" errors

**Solutions:**
1. Verify IAM user has CloudWatch and SNS permissions
2. Check user has these policies:
   - CloudWatchFullAccess
   - AmazonSNSFullAccess

Issue: Dashboard metrics not updating
-------------------------------------
**Symptoms:**
- Graphs show old data
- No recent data points

**Solutions:**
1. Dashboard auto-refreshes every 5 minutes
2. Click refresh button for immediate update
3. Check ECS service is still running
