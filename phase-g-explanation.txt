1. INTRODUCTION TO CI/CD
================================================================================

What is CI/CD?
--------------
CI/CD stands for Continuous Integration and Continuous Deployment (or Delivery).

**Continuous Integration (CI)**:
- Developers frequently merge code changes into a shared repository
- Each merge triggers automated builds and tests
- Catches bugs early, before they reach production
- "Integrate early, integrate often"

**Continuous Deployment (CD)**:
- Automatically deploy code to production after passing tests
- Every change that passes CI is deployed automatically
- No manual intervention required
- "If it passes tests, ship it"

**Continuous Delivery (also CD)**:
- Similar to Continuous Deployment
- But requires manual approval before production
- Good for regulated industries

Why CI/CD Matters
-----------------
Without CI/CD (Manual Process):
```
Developer writes code
    ↓
Developer manually builds
    ↓
Developer manually tests
    ↓
Developer creates Docker image
    ↓
Developer pushes to ECR
    ↓
Developer updates ECS service
    ↓
Takes 30-60 minutes, error-prone
```

With CI/CD (Automated):
```
Developer pushes code to GitHub
    ↓
Pipeline automatically:
  - Pulls code
  - Builds Docker image
  - Runs tests
  - Pushes to ECR
  - Deploys to ECS
    ↓
Takes 5-10 minutes, consistent
```

Benefits of CI/CD:
- **Speed**: Deploy in minutes, not hours
- **Consistency**: Same process every time
- **Reliability**: Automated tests catch bugs
- **Confidence**: Easy rollback if needed
- **Productivity**: Developers focus on code, not deployment

CI/CD Pipeline Stages
---------------------
A typical CI/CD pipeline has these stages:

1. **Source**: Get code from repository
2. **Build**: Compile/build the application
3. **Test**: Run automated tests
4. **Deploy**: Deploy to environment

Our Pipeline:
```
Source (GitHub) → Build (Docker) → Deploy (ECS)
```

We skipped the Test stage for simplicity, but in production you'd add:
- Unit tests
- Integration tests
- Security scans

4. CODESTAR CONNECTIONS (GITHUB INTEGRATION)
================================================================================

What is CodeStar Connections?
-----------------------------
CodeStar Connections is AWS's service for connecting to external source
control providers like GitHub, Bitbucket, and GitLab.

Why not just use GitHub directly?
- AWS needs secure, persistent access to your repository
- OAuth tokens ensure proper authorization
- Webhooks enable automatic pipeline triggers
- No need to store GitHub credentials in AWS

Connection Configuration
------------------------
```hcl
resource "aws_codestarconnections_connection" "github" {
  name          = "proj2-github-connection"
  provider_type = "GitHub"
}
```

That's all the Terraform code! But there's a catch...

Manual Approval Required
------------------------
After Terraform creates the connection, it's in "PENDING" status.
You must manually approve it in the AWS Console:

1. Go to: Settings → Connections (in CodePipeline console)
2. Select "proj2-github-connection"
3. Click "Update pending connection"
4. Authorize AWS Connector for GitHub
5. Select your GitHub account/organization
6. Grant access to repositories
7. Connection becomes "AVAILABLE"

Why manual? Security. AWS won't automatically get access to your
GitHub without explicit authorization.

How the Connection Works
------------------------
```
1. Initial Setup:
   AWS ─── OAuth Request ───→ GitHub
   AWS ←── OAuth Token ─────── GitHub
   Connection status: AVAILABLE

2. When Pipeline Runs:
   CodePipeline ─── "Get code" ───→ CodeStar Connection
   CodeStar ─────── API Call ─────→ GitHub
   GitHub ──────── Source Code ───→ S3 Artifact Bucket
```

Webhook Integration
-------------------
When you approve the connection, AWS also sets up a webhook in GitHub:

- GitHub notifies AWS on every push
- AWS starts the pipeline automatically
- No polling required (faster triggers)

You can see this webhook in:
GitHub → Repository → Settings → Webhooks

5. CODEBUILD DEEP DIVE
================================================================================

What is CodeBuild?
------------------
CodeBuild is a fully managed build service. You define what to build,
and AWS provides the compute environment.

Think of it as:
- Jenkins, but serverless
- CI server without servers to manage
- Pay only for build minutes

Build Environment
-----------------
```hcl
environment {
  compute_type                = "BUILD_GENERAL1_SMALL"
  image                       = "aws/codebuild/amazonlinux2-x86_64-standard:5.0"
  type                        = "LINUX_CONTAINER"
  image_pull_credentials_type = "CODEBUILD"
  privileged_mode             = true
}
```

**compute_type**: How much CPU/memory
- BUILD_GENERAL1_SMALL: 3 GB memory, 2 vCPUs
- BUILD_GENERAL1_MEDIUM: 7 GB memory, 4 vCPUs
- BUILD_GENERAL1_LARGE: 15 GB memory, 8 vCPUs

We use SMALL because our build is simple.

**image**: The build environment
- aws/codebuild/amazonlinux2-x86_64-standard:5.0
- Pre-installed: Docker, AWS CLI, Python, Node.js, etc.
- You can also use custom Docker images

**type**: Container type
- LINUX_CONTAINER: Standard Linux builds
- WINDOWS_CONTAINER: Windows builds
- ARM_CONTAINER: ARM architecture

**privileged_mode**: CRITICAL for Docker builds!
- true: Can run Docker-in-Docker
- false: Cannot run Docker commands
- Must be true for `docker build` to work

Environment Variables
---------------------
```hcl
environment_variable {
  name  = "AWS_ACCOUNT_ID"
  value = var.aws_account_id
}

environment_variable {
  name  = "AWS_REGION"
  value = var.aws_region
}

environment_variable {
  name  = "ECR_REPOSITORY_NAME"
  value = var.ecr_repository_name
}

environment_variable {
  name  = "CONTAINER_NAME"
  value = "proj2-app"
}
```

These variables are available in buildspec.yml as $AWS_ACCOUNT_ID, etc.

Build Artifacts
---------------
```hcl
artifacts {
  type = "CODEPIPELINE"
}
```

Type "CODEPIPELINE" means:
- Input artifacts come from CodePipeline
- Output artifacts go back to CodePipeline
- S3 bucket is managed by the pipeline

Source Configuration
--------------------
```hcl
source {
  type      = "CODEPIPELINE"
  buildspec = "buildspec.yml"
}
```

- type: Where code comes from (CodePipeline passes it)
- buildspec: Build instructions file (in repo root)

Build Logs
----------
```hcl
logs_config {
  cloudwatch_logs {
    group_name  = "/aws/codebuild/proj2-build"
    stream_name = "build-log"
  }
}
```

All build output goes to CloudWatch Logs.
Useful for debugging failed builds.

CodeBuild Pricing
-----------------

- Our build takes ~2 minutes
- Cost per build: ~$0.01

Very cost-effective!

6. CODEPIPELINE DEEP DIVE
================================================================================

What is CodePipeline?
---------------------
CodePipeline is an orchestration service. It doesn't actually build or
deploy - it coordinates other services that do.

Think of it as:
- A workflow engine
- A state machine for deployments
- The conductor that coordinates the orchestra

Pipeline Structure
------------------
```hcl
resource "aws_codepipeline" "proj2_pipeline" {
  name     = "proj2-pipeline"
  role_arn = aws_iam_role.codepipeline_role.arn

  artifact_store {
    location = aws_s3_bucket.codepipeline_artifacts.bucket
    type     = "S3"
  }

  stage { ... }  # Source
  stage { ... }  # Build
  stage { ... }  # Deploy
}
```

**name**: Pipeline identifier
**role_arn**: IAM role for pipeline operations
**artifact_store**: Where to store files between stages

Stage 1: Source
---------------
```hcl
stage {
  name = "Source"

  action {
    name             = "Source"
    category         = "Source"
    owner            = "AWS"
    provider         = "CodeStarSourceConnection"
    version          = "1"
    output_artifacts = ["source_output"]

    configuration = {
      ConnectionArn    = aws_codestarconnections_connection.github.arn
      FullRepositoryId = var.github_repository
      BranchName       = var.github_branch
    }
  }
}
```

**category**: Type of action (Source, Build, Deploy, Test, etc.)
**provider**: Which service handles this action
**output_artifacts**: Name for the output (used by next stage)
**configuration**: Provider-specific settings
  - ConnectionArn: The CodeStar connection
  - FullRepositoryId: "CharithKapuluru/proj2-ecs-fargate"
  - BranchName: "main"

What happens:
1. CodePipeline uses CodeStar to access GitHub
2. Downloads the repository code
3. Zips it and stores in S3 as "source_output"

Stage 2: Build
--------------
```hcl
stage {
  name = "Build"

  action {
    name             = "Build"
    category         = "Build"
    owner            = "AWS"
    provider         = "CodeBuild"
    input_artifacts  = ["source_output"]
    output_artifacts = ["build_output"]
    version          = "1"

    configuration = {
      ProjectName = aws_codebuild_project.proj2_build.name
    }
  }
}
```

**input_artifacts**: Uses output from Source stage
**output_artifacts**: Produces artifacts for Deploy stage
**ProjectName**: Which CodeBuild project to run

What happens:
1. CodePipeline starts CodeBuild project
2. CodeBuild downloads "source_output" from S3
3. Runs buildspec.yml commands
4. Uploads "build_output" (imagedefinitions.json) to S3

Stage 3: Deploy
---------------
```hcl
stage {
  name = "Deploy"

  action {
    name            = "Deploy"
    category        = "Deploy"
    owner           = "AWS"
    provider        = "ECS"
    input_artifacts = ["build_output"]
    version         = "1"

    configuration = {
      ClusterName = aws_ecs_cluster.proj2_cluster.name
      ServiceName = aws_ecs_service.proj2_service.name
      FileName    = "imagedefinitions.json"
    }
  }
}
```

**provider**: "ECS" - built-in ECS deployment support
**FileName**: File containing image information

What happens:
1. CodePipeline reads imagedefinitions.json from build_output
2. Creates new ECS task definition with new image
3. Updates ECS service to use new task definition
4. ECS performs rolling deployment

imagedefinitions.json Format
----------------------------
```json
[
  {
    "name": "proj2-app",
    "imageUri": "501894534533.dkr.ecr.us-east-1.amazonaws.com/proj2-app:e639af5"
  }
]
```

- name: Container name in task definition
- imageUri: Full ECR image URI with tag

Pipeline Execution States
-------------------------
Each stage/action can be in these states:
- **InProgress**: Currently running
- **Succeeded**: Completed successfully
- **Failed**: Encountered an error
- **Abandoned**: Pipeline was superseded

Pipeline Triggers
-----------------
The pipeline runs when:
1. **Webhook**: GitHub push triggers CodeStar webhook
2. **Manual**: Click "Release change" in console
3. **CLI**: `aws codepipeline start-pipeline-execution`
4. **Schedule**: Can add CloudWatch Events rule

7. THE BUILDSPEC.YML EXPLAINED
================================================================================

What is buildspec.yml?
----------------------
The buildspec.yml file contains build instructions for CodeBuild.
It's like a Makefile or script that defines the build process.

Location: Repository root (/proj2-ecs-fargate/buildspec.yml)

Our buildspec.yml
-----------------
```yaml
version: 0.2

phases:
  pre_build:
    commands:
      - echo "=== Pre-Build Phase ==="
      - echo "Logging in to Amazon ECR..."
      - aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
      - echo "Setting up environment variables..."
      - REPOSITORY_URI=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$ECR_REPOSITORY_NAME
      - COMMIT_HASH=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7)
      - IMAGE_TAG=$COMMIT_HASH
      - echo "Repository URI is $REPOSITORY_URI"
      - echo "Image Tag is $IMAGE_TAG"

  build:
    commands:
      - echo "=== Build Phase ==="
      - echo "Building Docker image..."
      - cd app
      - docker build -t $REPOSITORY_URI:latest .
      - docker tag $REPOSITORY_URI:latest $REPOSITORY_URI:$IMAGE_TAG
      - echo "Docker image built successfully"

  post_build:
    commands:
      - echo "=== Post-Build Phase ==="
      - echo "Pushing Docker image to ECR..."
      - docker push $REPOSITORY_URI:latest
      - docker push $REPOSITORY_URI:$IMAGE_TAG
      - echo "Docker image pushed successfully"
      - echo "Creating imagedefinitions.json for ECS deployment..."
      - cd ..
      - printf '[{"name":"%s","imageUri":"%s"}]' $CONTAINER_NAME $REPOSITORY_URI:$IMAGE_TAG > imagedefinitions.json
      - cat imagedefinitions.json
      - echo "Build completed successfully!"

artifacts:
  files:
    - imagedefinitions.json
```

Structure Breakdown
-------------------

**version: 0.2**
- Buildspec syntax version
- 0.2 is the current recommended version

**phases**
- Defines build lifecycle stages
- Each phase runs sequentially

Available Phases:
1. **install**: Install dependencies
2. **pre_build**: Setup before build
3. **build**: Main build commands
4. **post_build**: After build completes

Phase: pre_build
----------------
```yaml
pre_build:
  commands:
    # Login to ECR
    - aws ecr get-login-password --region $AWS_REGION | docker login ...

    # Set up variables
    - REPOSITORY_URI=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$ECR_REPOSITORY_NAME
    - COMMIT_HASH=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7)
    - IMAGE_TAG=$COMMIT_HASH
```

**ECR Login**: Required before pushing images
- `aws ecr get-login-password`: Gets temporary token
- `docker login`: Authenticates Docker client

**COMMIT_HASH**: Uses git commit hash as image tag
- $CODEBUILD_RESOLVED_SOURCE_VERSION: Full commit SHA
- `cut -c 1-7`: First 7 characters (e639af5)

This creates unique, traceable image tags.

Phase: build
------------
```yaml
build:
  commands:
    - cd app
    - docker build -t $REPOSITORY_URI:latest .
    - docker tag $REPOSITORY_URI:latest $REPOSITORY_URI:$IMAGE_TAG
```

**cd app**: Dockerfile is in /app directory
**docker build**: Creates the image
**docker tag**: Adds commit-specific tag

We create two tags:
- `latest`: Always points to newest build
- `e639af5`: Specific commit (immutable)

Phase: post_build
-----------------
```yaml
post_build:
  commands:
    - docker push $REPOSITORY_URI:latest
    - docker push $REPOSITORY_URI:$IMAGE_TAG
    - cd ..
    - printf '[{"name":"%s","imageUri":"%s"}]' $CONTAINER_NAME $REPOSITORY_URI:$IMAGE_TAG > imagedefinitions.json
```

**docker push**: Upload images to ECR
**imagedefinitions.json**: Required for ECS deploy action

Important: post_build runs even if build fails!
Use `on-failure: ABORT` in production to prevent this.

Artifacts Section
-----------------
```yaml
artifacts:
  files:
    - imagedefinitions.json
```

This tells CodeBuild what files to pass to the next stage.
The imagedefinitions.json file is zipped and uploaded to S3.

Environment Variables Available
-------------------------------
CodeBuild provides many built-in variables:

| Variable | Description |
|----------|-------------|
| CODEBUILD_BUILD_ID | Unique build identifier |
| CODEBUILD_BUILD_NUMBER | Build number |
| CODEBUILD_RESOLVED_SOURCE_VERSION | Git commit hash |
| CODEBUILD_SRC_DIR | Source directory path |
| AWS_REGION | Region (from environment config) |

Plus our custom variables:
- AWS_ACCOUNT_ID
- ECR_REPOSITORY_NAME
- CONTAINER_NAME

8. IAM ROLES AND PERMISSIONS
================================================================================

Why Two IAM Roles?
------------------
We need separate roles for different services:

1. **CodeBuild Role**: What CodeBuild can do
2. **CodePipeline Role**: What CodePipeline can do

Each service assumes its respective role.

CodeBuild IAM Role
------------------
```hcl
resource "aws_iam_role" "codebuild_role" {
  name = "proj2-codebuild-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = { Service = "codebuild.amazonaws.com" }
      Action = "sts:AssumeRole"
    }]
  })
}
```

Trust policy allows CodeBuild service to assume this role.

CodeBuild Permissions
---------------------
```hcl
resource "aws_iam_role_policy" "codebuild_policy" {
  policy = jsonencode({
    Statement = [
      {
        # CloudWatch Logs - write build logs
        Action = [
          "logs:CreateLogGroup",
          "logs:CreateLogStream",
          "logs:PutLogEvents"
        ]
        Resource = "arn:aws:logs:*:*:log-group:/aws/codebuild/*"
      },
      {
        # S3 - read input, write output artifacts
        Action = [
          "s3:GetObject",
          "s3:GetObjectVersion",
          "s3:PutObject"
        ]
        Resource = "${aws_s3_bucket.codepipeline_artifacts.arn}/*"
      },
      {
        # ECR - get auth token
        Action = ["ecr:GetAuthorizationToken"]
        Resource = "*"
      },
      {
        # ECR - push/pull images
        Action = [
          "ecr:BatchCheckLayerAvailability",
          "ecr:GetDownloadUrlForLayer",
          "ecr:BatchGetImage",
          "ecr:PutImage",
          "ecr:InitiateLayerUpload",
          "ecr:UploadLayerPart",
          "ecr:CompleteLayerUpload"
        ]
        Resource = "arn:aws:ecr:*:*:repository/proj2-app"
      }
    ]
  })
}
```

Permission breakdown:
- **logs:***: Write build logs to CloudWatch
- **s3:***: Read/write pipeline artifacts
- **ecr:GetAuthorizationToken**: Required for `docker login`
- **ecr:PutImage, etc.**: Push Docker images

CodePipeline IAM Role
---------------------
```hcl
resource "aws_iam_role" "codepipeline_role" {
  name = "proj2-codepipeline-role"

  assume_role_policy = jsonencode({
    Statement = [{
      Principal = { Service = "codepipeline.amazonaws.com" }
      Action = "sts:AssumeRole"
    }]
  })
}
```

CodePipeline Permissions
------------------------
```hcl
policy = jsonencode({
  Statement = [
    {
      # S3 - manage artifacts
      Action = ["s3:GetObject", "s3:PutObject", ...]
      Resource = [bucket_arn, bucket_arn/*]
    },
    {
      # CodeStar - use GitHub connection
      Action = ["codestar-connections:UseConnection"]
      Resource = connection_arn
    },
    {
      # CodeBuild - start builds
      Action = ["codebuild:BatchGetBuilds", "codebuild:StartBuild"]
      Resource = codebuild_project_arn
    },
    {
      # ECS - deploy to cluster
      Action = ["ecs:*"]
      Resource = "*"
    },
    {
      # IAM - pass role to ECS
      Action = ["iam:PassRole"]
      Resource = "*"
    }
  ]
})
```

Permission breakdown:
- **s3:***: Read source, store artifacts
- **codestar-connections:UseConnection**: Access GitHub
- **codebuild:***: Start and monitor builds
- **ecs:***: Update services, register task definitions
- **iam:PassRole**: Required for ECS to use task execution role

The PassRole Permission
-----------------------
Why is `iam:PassRole` needed?

When CodePipeline updates ECS, it creates a new task definition.
The task definition references the task execution role.
AWS requires explicit permission to "pass" a role to another service.

Without PassRole:
```
CodePipeline: "ECS, use this task definition with role X"
AWS: "You can't give role X to ECS without iam:PassRole permission"
```

End-to-End Execution
--------------------

**Trigger: Developer pushes to GitHub**
```bash

**Step 1: GitHub Webhook (Instant)**
```
GitHub ──webhook──→ AWS CodeStar Connection
                          │
                          ▼
              "New push to main branch"
                          │
                          ▼
              Start CodePipeline
```

**Step 2: Source Stage (~30 seconds)**
```
CodePipeline ──"get code"──→ CodeStar Connection
                                    │
                                    ▼
                              GitHub API
                                    │
                                    ▼
                         Download repository
                                    │
                                    ▼
                    Zip and upload to S3 (source_output)

**Step 3: Build Stage (~2 minutes)**
```
CodePipeline ──"start build"──→ CodeBuild
                                    │
                                    ▼
                         Provision build container
                                    │
                                    ▼
                         Download source_output from S3
                                    │
                                    ▼
                         Run buildspec.yml:
                           - Login to ECR
                           - docker build
                           - docker push
                           - Create imagedefinitions.json
                                    │
                                    ▼
                         Upload build_output to S3
```

**Step 4: Deploy Stage (~3-5 minutes)**
```
CodePipeline ──"deploy to ECS"──→ ECS Service
                                       │
                                       ▼
                            Read imagedefinitions.json
                                       │
                                       ▼
                            Create new task definition

                                       │
                                       ▼
                            Update ECS service
                                       │
                                       ▼
                            Rolling deployment:
                              1. Start new task
                              2. Wait for healthy
                              3. Stop old task
                                       │
                                       ▼
                            New version live!
```

CI/CD Concepts
--------------
- **Continuous Integration**: Automated build/test on code changes
- **Continuous Deployment**: Automated deployment after CI
- **Pipeline**: Series of stages that process code
- **Artifact**: Output from one stage, input to next

AWS Services
------------
- **CodePipeline**: Orchestrates CI/CD workflow
- **CodeBuild**: Serverless build environment
- **CodeStar Connections**: OAuth to external Git providers
- **S3**: Artifact storage between stages

Key Files
---------
- **buildspec.yml**: Build instructions for CodeBuild
- **imagedefinitions.json**: Image info for ECS deploy
- **codepipeline.tf**: Infrastructure as Code for pipeline

Pipeline Stages
---------------
1. **Source**: Get code from GitHub
2. **Build**: Create Docker image, push to ECR
3. **Deploy**: Update ECS service

Triggers
--------
- Push to GitHub → Webhook → Pipeline starts
- Manual: Console or CLI
- Scheduled: CloudWatch Events (not configured)

Best Practices
--------------
1. Use commit hash for image tags (traceability)
2. Store secrets in Secrets Manager, not buildspec
3. Use smallest compute type that works
4. Set reasonable timeouts
5. Monitor build logs for issues

13. COMMON ISSUES AND SOLUTIONS
================================================================================

Issue: Pipeline stuck on Source stage
-------------------------------------
**Symptoms:**
- Source stage shows "InProgress" indefinitely
- No error message

**Causes:**
- CodeStar connection not approved
- GitHub webhook not set up

**Solutions:**
1. Check connection status:
   ```bash
   aws codestarconnections get-connection \
     --connection-arn <connection-arn>
   ```
2. Status should be "AVAILABLE", not "PENDING"
3. If PENDING, approve in AWS Console

Issue: Build fails immediately
------------------------------
**Symptoms:**
- Build stage fails in seconds
- "YAML_FILE_ERROR" in logs

**Causes:**
- Invalid buildspec.yml syntax
- Missing buildspec.yml file

**Solutions:**
1. Validate YAML syntax online
2. Check file is in repository root
3. Common YAML issues:
   - Indentation (use spaces, not tabs)
   - Special characters need quoting

Issue: Docker build fails
-------------------------
**Symptoms:**
- "Cannot connect to Docker daemon"
- "docker: command not found"

**Causes:**
- privileged_mode not enabled
- Wrong build image

**Solutions:**
1. Ensure `privileged_mode = true` in CodeBuild
2. Use standard CodeBuild image with Docker

Issue: Docker Hub rate limit
----------------------------
**Symptoms:**
- "429 Too Many Requests"
- "toomanyrequests: pull rate limit exceeded"

**Causes:**
- Docker Hub limits anonymous pulls
- CodeBuild doesn't authenticate to Docker Hub

**Solutions:**
1. Use AWS Public ECR instead:
   ```dockerfile
   FROM public.ecr.aws/docker/library/python:3.11-slim
   ```
2. Or authenticate to Docker Hub in buildspec

Issue: ECR push fails
--------------------
**Symptoms:**
- "denied: Your authorization token has expired"
- "no basic auth credentials"

**Causes:**
- ECR login expired or failed
- Wrong repository name

**Solutions:**
1. Ensure ECR login is in pre_build phase
2. Check repository name matches
3. Verify CodeBuild role has ECR permissions

Issue: ECS deploy fails
-----------------------
**Symptoms:**
- Deploy stage fails
- "PermissionError: insufficient permissions"

**Causes:**
- CodePipeline role missing ECS permissions
- Missing iam:PassRole permission

**Solutions:**
1. Add ecs:* permissions to CodePipeline role
2. Add iam:PassRole permission
3. Check task execution role is correct

Issue: Deploy succeeds but app unchanged
----------------------------------------
**Symptoms:**
- Pipeline shows success
- App still shows old version

**Causes:**
- Wrong container name in imagedefinitions.json
- Image wasn't actually pushed

**Solutions:**
1. Check imagedefinitions.json has correct container name
2. Verify image exists in ECR with correct tag
3. Check ECS task is using new image

Debugging Checklist
-------------------
1. ✓ CodeStar connection is AVAILABLE
2. ✓ buildspec.yml exists in repo root
3. ✓ buildspec.yml has valid YAML syntax
4. ✓ CodeBuild has privileged_mode = true
5. ✓ Dockerfile uses public.ecr.aws base image
6. ✓ ECR login happens before docker push
7. ✓ imagedefinitions.json has correct container name
8. ✓ CodePipeline role has ECS and PassRole permissions
9. ✓ Build logs show no errors
